## 1. Authority Boundary

The Job Engine is the durable execution authority upstream of provider adapters,
webhooks, retries, reconciliation, and asset registration.

Dynaxis Jobs are canonical platform records. External provider jobs are
downstream execution details. A provider adapter, provider webhook, worker
process, queue message, poller, or provider credential may supply *evidence*,
but none of them owns the Dynaxis Job lifecycle.

Required execution order:

```text
Generation Gateway / authorized caller
  -> Dynaxis Generation request context
  -> Dynaxis Job created
  -> Job Engine state transition
  -> queue / worker / provider adapter
  -> provider job id and provider status evidence
  -> Job Engine state transition
  -> output normalization
  -> asset registration
  -> terminal Job state
```

Asset registration is downstream of the Job Engine. A provider-reported success
is not a Dynaxis success until the Job Engine has validated output references,
registered required Assets or artifact records, and written the terminal
transition.

Provider credentials, model accounts, provider job ids, worker ids, queue
leases, and webhook signatures **must never become Dynaxis identity or
authorization subjects**. This restates the Phase 7D security review finding
that provider credentials are not identity.

## 2. Job Identity

### 2.1 Dynaxis Job id

Canonical, immutable identifier for execution state.

- Generated by Dynaxis before provider submission.
- Scoped by the canonical ownership chain: Job -> Project -> Workspace.
- Primary correlation key for Generations, Assets, audit timeline entries,
  retries, cancellation, reconciliation, and later public API surfaces.
- Used for `job.read`, `job.cancel`, `job.retry` permission checks.
- Must not be replaced by, derived from, or encoded into a provider job id.

### 2.2 Provider job id

Provider-originated metadata returned after submit or callback.

- May be null before the provider accepts a submission.
- **Not** globally unique; meaningful only with provider id plus
  ProviderConnection id or provider account scope.
- **Not** an authorization credential; grants no permission.
- Must not be the primary public Dynaxis Job lookup key.
- May change across attempts. Must be stored in attempt-scoped history; a
  job-level pointer may exist only as the latest value for polling/webhook
  correlation.
- Treated as untrusted input: bounded length, sanitized for logs, never proof
  that a transition is valid.

Minimum callback-correlation key for WP-7E-04:

```text
provider_id + provider_connection_id_or_legacy_owner_scope + provider_job_id
```

Legacy MuAPI owner scope may be used **only** as compatibility metadata and must
not become new identity (Phase 7D residual risk R6).

## 3. Canonical States

Source of truth: `JOB_STATES` in `lib/dynaxis/jobs/contracts.js`.

| State | Terminal | Meaning | Provider job id expectation |
|---|---|---|---|
| `queued` | no | Accepted and persisted; eligible for dispatch or delayed retry. | Usually null. |
| `leased` | no | Dispatcher holds a lease and is preparing or performing provider submit / worker handoff. | Usually null; may appear at end of submit. |
| `running` | no | Provider, worker, poller, or webhook evidence says execution is in progress. | Usually present for external providers. |
| `waiting_retry` | no | A retryable failure, lease expiry, rate limit, outage, or reconciliation decision scheduled another attempt. | May retain the failed attempt's id in history. |
| `timed_out` | **no** | A Dynaxis deadline was exceeded. See §3.1 and §10 — this is **not** terminal in the current contract. | Optional. |
| `completed` | **yes** | Success evidence accepted **and** all required output registration committed. | Present when an external provider produced one. |
| `failed` | **yes** | Non-timeout failure that will not be retried automatically. | Optional. |
| `cancelled` | **yes** | Cancelled by authorized request or internal policy; no further output may be registered automatically. | Optional. |

`TERMINAL_JOB_STATES` = `completed`, `failed`, `cancelled` — exactly three.

### 3.1 Divergence from the earlier unmerged draft — decisions for WP-7E-04

The unmerged draft at `9fc4c3e` used a wider vocabulary. The scaffold on `main`
is authoritative; the mapping is recorded so nothing from the draft is lost.

| Draft state | Scaffold state on main | Note |
|---|---|---|
| `dispatching` | `leased` | Rename only. |
| `submitted` + `processing` | `running` | **Merged.** The scaffold does not distinguish provider-accepted from provider-executing. |
| `retry_scheduled` | `waiting_retry` | Rename only. |
| `succeeded` | `completed` | Rename only. |
| `cancelling` | *(absent)* | **No intermediate cancelling state exists.** See §9. |
| `timed_out` (terminal) | `timed_out` (**non-terminal**) | **Semantic change.** See below. |

Two open decisions that **WP-7E-04 must resolve explicitly before writing
schema**. Neither may be settled by silently changing the scaffold.

- **D1 — Is `timed_out` terminal?** The scaffold allows
  `timed_out -> waiting_retry | failed | cancelled`, making timeout a
  *recoverable* condition rather than an outcome. The draft treated it as a
  fourth terminal state. The scaffold behaviour is the more useful one (a
  timeout can legitimately be retried), but it means **a timed-out Job is not
  finished** and any UI, projection, or public API must not present it as such.
  WP-7E-04 must either keep it non-terminal and define the settling transition
  that ends a timed-out Job, or promote it to terminal and update
  `TERMINAL_JOB_STATES` under its own change.
- **D2 — Is an intermediate `cancelling` state needed?** The scaffold cancels
  directly to `cancelled` from every non-terminal state. This is simpler but
  loses the "cancellation requested, provider not yet confirmed" window, which
  matters when provider cancellation is asynchronous or unsupported. WP-7E-04
  must either accept direct cancellation and record the requested/confirmed
  distinction as *metadata*, or introduce `cancelling` as a state change.

Until D1 and D2 are decided, **treat the scaffold matrix as binding.**

## 4. Terminal State Rules

Terminal states are `completed`, `failed`, `cancelled`.

- Terminal state is immutable except for audited reconciliation metadata that
  does not change the state.
- Late provider callbacks, duplicate queue deliveries, stale workers, and manual
  polls cannot move a terminal Job back to a non-terminal state. `JOB_TRANSITIONS`
  encodes this: all three terminal states have an empty transition list.
- A terminal Job cannot create new retry attempts.
- A terminal Job cannot enqueue provider cancellation except as best-effort
  cleanup recorded as reconciliation metadata.
- Asset registration for a terminal non-success state is forbidden unless a
  later audited manual recovery package defines an explicit exception.
- `completed` requires output registration to commit **before** the terminal
  transition.

## 5. Allowed Transitions And Ownership

Only the Job Engine transition service may persist canonical state changes.
"Requested by" identifies who supplies evidence; it does not bypass the engine.

| From | To | Requested / evidenced by | Job Engine requirements |
|---|---|---|---|
| *(none)* | `queued` | Generation Gateway, authorized internal service | Project ownership and permission check passed; idempotency key accepted. |
| `queued` | `leased` | Queue dispatcher | Valid lease; Job not cancelled; provider/capability available. |
| `queued` | `cancelled` | Authorized request, internal policy | Never dispatched; finalize immediately. |
| `leased` | `running` | Worker adapter after submit | Attempt recorded; provider id matches Job; provider job id captured when available. |
| `leased` | `waiting_retry` | Worker adapter, dispatcher, reconciler | Retryable submit failure or lease expiry before acceptance; retry budget remains. |
| `leased` | `timed_out` | Lease monitor, reconciler | Lease or submit deadline exceeded. |
| `leased` | `failed` | Worker adapter, Job Engine | Non-retryable submit failure or budget exhausted. |
| `leased` | `cancelled` | Authorized request, internal policy | Lease and attempt marked cancellation-requested. |
| `running` | `completed` | Poller, webhook, worker adapter | Success evidence accepted; outputs normalized; assets registered in the same durable flow. |
| `running` | `waiting_retry` | Poller, webhook, reconciler | Retryable provider error; existing execution safely abandoned or known failed; budget remains. |
| `running` | `timed_out` | Timeout scheduler, reconciler | Execution deadline exceeded. |
| `running` | `failed` | Poller, webhook, reconciler | Non-retryable provider failure or budget exhausted. |
| `running` | `cancelled` | Authorized request, internal policy | Provider cancellation attempted when supported; otherwise a Dynaxis policy decision. |
| `waiting_retry` | `queued` | Retry scheduler | Backoff elapsed; no cancellation requested; budget remains. |
| `waiting_retry` | `failed` | Retry scheduler, reconciler | Budget exhausted or policy disables further retries. |
| `waiting_retry` | `cancelled` | Authorized request, internal policy | Future retry suppressed. |
| `timed_out` | `waiting_retry` | Reconciler, retry scheduler | Retry budget remains and replay is safe (see D1). |
| `timed_out` | `failed` | Reconciler | Budget exhausted or replay unsafe. |
| `timed_out` | `cancelled` | Authorized request, internal policy | Cancellation after timeout. |

Forbidden, and enforced today by `canTransitionJobState`:

- Any terminal state to any state at all.
- Any state not listed in `JOB_TRANSITIONS[from]`.
- Provider evidence writing state without Job Engine validation.
- `queued` directly to `completed` for provider-backed generation jobs.

## 6. Failure Semantics

The scaffold classifies failures with `JOB_FAILURE_KINDS` in
`lib/dynaxis/jobs/state-machine.js`: `transient`, `permanent`, `cancelled`,
`timeout`. WP-7E-04 must map every normalized failure class below onto one of
those four kinds.

| Class | Kind | Retryable |
|---|---|---|
| `INVALID_REQUEST` | permanent | no |
| `AUTHORIZATION_DENIED` | permanent | no |
| `PROVIDER_AUTH_FAILED` | permanent | no, until the connection is repaired |
| `PROVIDER_RATE_LIMITED` | transient | yes, while budget remains |
| `PROVIDER_UNAVAILABLE` | transient | yes, while budget remains |
| `PROVIDER_REJECTED` | permanent | usually no; only if resolver policy changes the request |
| `PROVIDER_FAILED` | permanent | only when the provider error taxonomy says replay is safe |
| `WORKER_FAILED` | transient | yes, when the attempt can be safely replayed |
| `LEASE_EXPIRED` | transient | yes, unless submission ambiguity requires reconciliation first |
| `OUTPUT_INVALID` | permanent | only when a fresh attempt is safe |
| `ASSET_REGISTRATION_FAILED` | transient | yes, if idempotency prevents duplicate registration |
| `CANCEL_FAILED` | cancelled | n/a — does not by itself mean the Job failed |
| `TIMEOUT` | timeout | see §10 and D1 |

Error messages persisted to Job records must be **user-safe, redacted, and
bounded**. Detailed provider payloads remain sanitized diagnostics only. The
redaction key list is shared with the event model — see
`PHASE_7E_JOB_EVENT_MODEL.md` §3.

## 7. Cancellation Semantics

Cancellation is a Dynaxis policy decision, not a provider guarantee.

- Only a principal with `job.cancel`, or an explicit internal service policy,
  may request cancellation.
- The request records `cancel_requested_at`, requesting-actor metadata, and a
  reason.
- From `queued` or `waiting_retry`, cancellation finalizes immediately.
- From `leased` or `running`, the engine asks the active adapter to cancel when
  supported, then finalizes. **There is no `cancelling` state in the current
  contract** — the requested/confirmed distinction must be carried as metadata
  unless D2 introduces one.
- If provider cancellation is unsupported, the engine may still finalize as
  `cancelled` after suppressing Dynaxis retries, recording that external
  execution may continue outside Dynaxis control.
- Late provider **success** after `cancelled` must not register Assets
  automatically.
- Late provider **failure** after `cancelled` is reconciliation evidence only.
- A cancelled Job may be retried only by creating a **new** Dynaxis Job. The
  original stays terminal.

## 8. Idempotency Boundary

The scaffold provides `normalizeIdempotencyKey()` in
`lib/dynaxis/jobs/idempotency.js`: string required, trimmed, lowercased,
whitespace collapsed to `-`, non-empty, max **128** characters, otherwise
`INVALID_IDEMPOTENCY_KEY`.

That is a **normalization contract only**. It does not store or deduplicate
anything. WP-7E-04 owns the durable uniqueness constraint.

The key must bind:

```text
workspace/project scope
authorized actor or service principal
generation request fingerprint
capability/model/provider routing decision
client-supplied idempotency key when present
```

Idempotency must prevent duplicate Jobs for repeated submits, and duplicate
Assets for repeated completion attempts, across duplicate queue messages,
duplicate user retry clicks, process restarts, and webhook redelivery.

## 9. Retry Semantics

Retry creates a new **attempt** for the same Dynaxis Job. It does not create a
new Generation or duplicate Assets.

- Allowed only from non-terminal states, via `waiting_retry`.
- Bounded by `max_attempts`, total execution deadline, and provider policy.
- Backoff bounded, jittered where appropriate, recording `next_attempt_at`.
- Preserves the same Dynaxis Job id; may produce a new provider job id, and
  attempt history preserves all of them.
- Manual retry of a terminal `failed` Job must create a **new** Job linked by
  provenance metadata. It must not mutate the terminal state.

## 10. Timeout Semantics

Deadlines are owned by Dynaxis even when provider APIs have their own limits:
queue wait, lease, submit, provider acceptance, execution, cancellation, and
asset registration.

- Timeout before provider acceptance with budget remaining -> `waiting_retry`.
- Timeout after acceptance with ambiguous provider state -> reconciliation must
  run before retrying, unless the adapter declares replay safety.
- Budget exhausted or retry forbidden -> `timed_out`, then settled per D1.
- Every timeout transition must record **which deadline** was exceeded.

## 11. Recovery And Reconciliation Semantics

Reconciliation repairs divergence between durable Dynaxis state and external
evidence.

Responsibilities: find stale `leased`, `running`, `waiting_retry`, and
`timed_out` Jobs; resolve stale leases and worker crashes; poll providers when
webhooks are missing; detect uncorrelatable provider job ids; detect provider
terminal evidence arriving after Dynaxis terminal state; move retryable stuck
Jobs to `waiting_retry`; move exhausted ones to `failed`; record every decision
in the audit timeline.

Reconciliation must be conservative:

- Do not register Assets for a terminal non-success Job.
- Do not resurrect terminal Jobs.
- Do not trust provider success without output normalization and registration.
- Do not infer Workspace/Project authority from provider metadata.
- Do not silently change provider, model, Project, Generation, or ownership.

## 12. Generation And Asset Coupling

- A Job belongs to exactly one Project.
- A Job references the canonical Generation it executes, unless a later
  non-generation job type explicitly allows a null generation reference.
- Generation and Job provider ids must match for provider-backed work; Project
  ids must match.
- Assets reference the Dynaxis **Job id** that produced them, never the provider
  job id.

Recommended Generation projection (compatibility only; the Job Engine remains
source of truth):

| Job state | Generation status |
|---|---|
| `queued`, `leased`, `waiting_retry` | `submitted` |
| `running` | `processing` |
| `completed` | `succeeded` |
| `failed`, `timed_out` | `failed` |
| `cancelled` | `cancelled` |

`timed_out` projecting to `failed` is a **presentation** decision and does not
make the state terminal. See D1.

## 13. Security And Authorization

- `job.create`, `job.read`, `job.cancel`, `job.retry` use the Phase 7C policy
  vocabulary; inheritance is Job -> Project -> Workspace.
- Provider credentials and provider job ids grant no Job access.
- Webhook authentication verifies provider origin only; it grants no user
  authority.
- Worker adapters are not principals for user permissions.
- Internal service principals must be explicit, scoped, and audited.

**Phase 7D residual risk R1 remains binding.** Service principals are
fail-closed at the route guard, the policy evaluator, and the resolver.
`assertWorkerProviderConnectionBlocked()` in `lib/dynaxis/jobs/contracts.js`
throws `501` unconditionally, and `WORKER_PROVIDER_CONNECTION_POLICY.status` is
`blocked`. **WP-7E-06 must not use ProviderConnections until an explicit, tested
service-principal allowlist exists.** WP-7E-04 must not weaken this guard, and
persisting job state does not by itself resolve R1.

## 14. Validation Expectations

Currently satisfied by the scaffold on `main`:

- Unknown state or unknown target state raises `INVALID_JOB_STATE`.
- A transition absent from `JOB_TRANSITIONS` raises `INVALID_JOB_TRANSITION`.
- Terminal states expose an empty allowed-transition list.
- Idempotency keys normalize or raise `INVALID_IDEMPOTENCY_KEY`.

Required of WP-7E-04, not yet satisfied anywhere:

- Transitions are atomic and serialized per Job under concurrency.
- Duplicate evidence for the same attempt is idempotent.
- Terminal immutability survives late webhooks and restarts.
- Attempt history is append-only.
- Lease ownership is verified before a leased-state transition commits.

## 15. What WP-7E-04 Must Persist

At minimum, and subject to D1/D2:

- **Job record:** canonical id, Project id, Generation reference, provider id,
  capability/model routing decision, current state, attempt counter,
  `max_attempts`, deadline fields, `cancel_requested_at` and requesting actor,
  terminal reason, redacted user-safe error, timestamps.
- **Attempt history:** append-only per attempt — attempt number, lease id and
  holder, provider job id, submit/accept/complete timestamps, normalized
  failure class and kind, sanitized provider diagnostics.
- **Idempotency records:** durable uniqueness over the §8 binding, sufficient to
  return the original Job for a duplicate submit.
- **Lease records:** holder, acquired-at, expires-at, heartbeat, enough to let
  the reconciler detect expiry.
- **Event timeline:** see `PHASE_7E_JOB_EVENT_MODEL.md` §7.

Explicitly **not** owned by WP-7E-04: queue implementation (WP-7E-05), worker
runtime (WP-7E-06), webhook ingress (WP-7E-07), durable audit sink for Phase 7D
provider events (residual risk R3, still unowned).
