# Phase 7E - Job State Machine Specification

**Status:** WP-7E-01 specification handoff.
**Scope:** Documentation contract for the durable Dynaxis Job Engine. No runtime code, schema migration, queue worker, webhook route, provider adapter, or asset service behavior is implemented by this document.
**Depends on:** Generation Provider Kernel foundation, Phase 7C identity and Project ownership contracts, future Phase 7D ProviderConnection and secret storage contracts.
**Blocks:** WP-7E-04 Job Schema Migration and Persistence, WP-8E-01 Skill Manifest Registry and Package Format.

## 1. Authority Boundary

The Job Engine is the durable execution authority upstream of provider adapters, webhooks, retries, reconciliation, and asset registration.

Dynaxis Jobs are canonical platform records. External provider jobs are downstream execution details. A provider adapter, provider webhook, worker process, queue message, local poller, or provider credential may report evidence, but none of them owns the Dynaxis Job lifecycle.

The required execution order is:

```text
Generation Gateway / authorized caller
  -> create Dynaxis Generation request context
  -> create Dynaxis Job
  -> Job Engine state transition
  -> queue / worker / provider adapter
  -> provider job id and provider status evidence
  -> Job Engine state transition
  -> output normalization
  -> asset registration
  -> terminal Job state
```

Asset registration is downstream of the Job Engine. A provider-reported success is not a Dynaxis success until the Job Engine has validated output references, registered required Assets or artifact records, and written the terminal transition.

Provider credentials, model accounts, provider job ids, worker ids, queue leases, and webhook signatures must never become Dynaxis identity or authorization subjects.

## 2. Job Identity

### 2.1 Dynaxis Job id

The Dynaxis Job id is the canonical immutable identifier for execution state.

Rules:

- It is generated by Dynaxis before provider submission.
- It is scoped by the canonical Project ownership chain: Job -> Project -> Workspace.
- It is the primary correlation key for Generations, Assets, audit timeline entries, retries, cancellation, reconciliation, and later public API surfaces.
- It must be used for Dynaxis permissions such as `job.read`, `job.cancel`, and `job.retry`.
- It must not be replaced by, derived from, or encoded into a provider job id.
- It must not be sent to a provider unless the adapter explicitly needs a non-authoritative correlation token and the payload is safe to expose.

### 2.2 Provider job id

The provider job id is metadata returned by a provider after submit or callback.

Rules:

- It may be null before the provider accepts a submission.
- It is not globally unique. It is only meaningful with at least provider id and, once Phase 7D lands, ProviderConnection id or provider account scope.
- It is not an authorization credential and grants no permission.
- It must not be used as the primary public Dynaxis Job lookup key.
- It may change across retry attempts when a new provider execution is created.
- It must be stored in an attempt-scoped history. A job-level `provider_job_id` may exist only as the current/latest lookup pointer for status polling and webhook correlation.
- It must be treated as provider-originated input: bounded length, sanitized for logs, indexed for callback lookup, and never trusted as proof that a transition is valid.

The minimum future uniqueness expectation for callback lookup is:

```text
provider_id + provider_connection_id_or_legacy_owner_scope + provider_job_id
```

When ProviderConnection is not yet available, legacy MuAPI owner scope may be used only as compatibility metadata. It must not become new identity.

## 3. Canonical States

These states are the Phase 7E canonical state vocabulary. WP-7E-04 must persist this vocabulary directly or provide a documented compatibility mapping that preserves the same semantics.

| State | Terminal | Meaning | Provider job id expectation |
| --- | --- | --- | --- |
| `queued` | no | Dynaxis has accepted and persisted the Job. It is eligible for dispatch or delayed retry. | Usually null unless re-queued for polling/reconciliation after a provider submit. |
| `dispatching` | no | The Job Engine has leased work and is preparing or performing a provider submit or internal worker handoff. | Usually null. |
| `submitted` | no | A provider or worker adapter has accepted the work. Dynaxis is awaiting provider execution evidence. | Usually present for external providers. |
| `processing` | no | Provider, worker, poller, or webhook evidence says execution has started or is in progress. | Usually present for external providers. |
| `retry_scheduled` | no | A retryable failure, lease expiry, rate limit, outage, or reconciliation decision has scheduled another attempt. | May retain the failed attempt's provider job id in attempt history; the next attempt may receive a new provider job id. |
| `cancelling` | no | A cancellation request has been accepted by Dynaxis and the Job Engine is stopping queued work, active leases, provider execution, or future retries. | Optional. Required only if provider cancellation/reconciliation needs it. |
| `succeeded` | yes | Provider or worker success evidence has been accepted and all required Dynaxis output registration has committed. | Present when external provider produced a provider job id. |
| `failed` | yes | The Job reached a non-timeout failure that will not be retried automatically. | Optional. |
| `cancelled` | yes | The Job was cancelled by an authorized Dynaxis request or internal policy and no further provider output may be registered for it automatically. | Optional. |
| `timed_out` | yes | The Job exceeded a Dynaxis execution, provider, lease, or cancellation deadline and will not be retried automatically. | Optional. |

Current pre-7E lifecycle rows use `queued`, `submitted`, `processing`, `succeeded`, `failed`, and `cancelled`. Migration must preserve those rows without destructive rewrite. Where historical data has only `failed` plus a timeout error code, WP-7E-04 may either retain `failed` or map to `timed_out` only when evidence is deterministic.

## 4. Terminal State Rules

Terminal states are:

- `succeeded`
- `failed`
- `cancelled`
- `timed_out`

Terminal rules:

- Terminal state is immutable except for audited reconciliation metadata that does not change the terminal state.
- Late provider callbacks, duplicate queue deliveries, stale workers, and manual polls cannot move a terminal Job back to a non-terminal state.
- A terminal Job cannot create new retry attempts.
- A terminal Job cannot enqueue provider cancellation, except for best-effort cleanup recorded as reconciliation metadata.
- Asset registration for a terminal non-success state is forbidden unless a later audited manual recovery package explicitly defines an exception.
- `succeeded` requires output registration to commit before the terminal transition.

## 5. Allowed Transitions And Ownership

Only the Job Engine transition service may persist canonical state changes. Owners below identify who may request or supply evidence for the transition. They do not bypass the Job Engine.

| From | To | Requested or evidenced by | Job Engine requirements |
| --- | --- | --- | --- |
| none | `queued` | Generation Gateway, authorized internal service, future Skill/App/Build caller | Project ownership and permission check passed; idempotency key accepted; Generation/Job invariant established. |
| `queued` | `dispatching` | Queue dispatcher | Valid lease; Job not cancelled or terminal; provider/capability still available. |
| `dispatching` | `submitted` | Worker adapter after provider submit | Submit attempt recorded; provider id matches Job; provider job id captured when available; sanitized provider payload stored. |
| `submitted` | `processing` | Provider poller, webhook, worker adapter, reconciler | Evidence correlates to the active attempt; provider status normalizes to in-progress. |
| `processing` | `processing` | Provider poller, webhook, worker adapter | Progress or metadata update only; no state regression. |
| `submitted` | `succeeded` | Provider poller, webhook, worker adapter | Success evidence accepted; outputs normalized; assets/artifacts registered in the same durable completion flow. |
| `processing` | `succeeded` | Provider poller, webhook, worker adapter | Same as `submitted -> succeeded`. |
| `dispatching` | `retry_scheduled` | Worker adapter, dispatcher, reconciler | Submit failed with retryable normalized error or lease expired before provider acceptance; retry budget remains. |
| `submitted` | `retry_scheduled` | Provider poller, webhook, reconciler | Provider state/error is retryable, no terminal output committed, retry budget remains. |
| `processing` | `retry_scheduled` | Provider poller, webhook, reconciler | Provider state/error is retryable, existing provider execution is safely abandoned or known failed, retry budget remains. |
| `retry_scheduled` | `queued` | Retry scheduler | Backoff delay elapsed; cancellation has not been requested; retry budget remains. |
| `queued` | `cancelling` | Authorized API request, internal policy | Cancellation permission checked or internal policy allowed; terminal state not already reached. |
| `dispatching` | `cancelling` | Authorized API request, internal policy, stale lease reconciler | Lease and active attempt marked cancellation-requested. |
| `submitted` | `cancelling` | Authorized API request, internal policy | Provider cancellation attempted when supported; otherwise cancellation remains a Dynaxis policy decision. |
| `processing` | `cancelling` | Authorized API request, internal policy | Same as `submitted -> cancelling`. |
| `retry_scheduled` | `cancelling` | Authorized API request, internal policy | Future retry suppressed. |
| `cancelling` | `cancelled` | Job Engine, provider adapter, reconciler | Queue/lease/retry suppressed; provider cancellation succeeded, is unsupported, or is no longer needed; no success committed. |
| `queued` | `cancelled` | Job Engine | Job had not reached provider execution and cancellation can be finalized immediately. |
| `dispatching` | `failed` | Worker adapter, Job Engine | Non-retryable submit failure or retry budget exhausted. |
| `submitted` | `failed` | Provider poller, webhook, reconciler | Non-retryable provider failure or retry budget exhausted. |
| `processing` | `failed` | Provider poller, webhook, reconciler | Non-retryable provider failure or retry budget exhausted. |
| `retry_scheduled` | `failed` | Retry scheduler, reconciler | Retry budget exhausted or policy disables further retries before redispatch. |
| `queued` | `timed_out` | Timeout scheduler, reconciler | Queue wait deadline exceeded and retry policy does not allow another attempt. |
| `dispatching` | `timed_out` | Lease monitor, reconciler | Lease or submit deadline exceeded and retry policy does not allow another attempt. |
| `submitted` | `timed_out` | Timeout scheduler, reconciler | Provider acceptance deadline or total execution deadline exceeded and retry policy does not allow another attempt. |
| `processing` | `timed_out` | Timeout scheduler, reconciler | Provider execution deadline exceeded and retry policy does not allow another attempt. |
| `cancelling` | `timed_out` | Timeout scheduler, reconciler | Cancellation deadline exceeded and policy chooses timeout rather than cancellation finalization. |

Forbidden transitions:

- Any terminal state to any non-terminal state.
- Any terminal state to a different terminal state.
- `succeeded` to `failed`, `cancelled`, or `timed_out`.
- `failed`, `cancelled`, or `timed_out` to `succeeded`.
- `queued` directly to `succeeded` for provider-backed generation jobs.
- Provider evidence directly writing any state without Job Engine validation.

## 6. Transition Ownership Details

### Generation Gateway

The Generation Gateway or authorized caller may request Job creation. It must provide Project context, Generation context when applicable, requested capability/model/provider, actor context, idempotency key when available, and provenance references. It does not dispatch directly to external providers once Phase 7E durable execution is active.

### Queue dispatcher

The queue dispatcher may request `queued -> dispatching` and `retry_scheduled -> queued` only through the Job Engine. Queue messages are hints, not the source of truth. Duplicate messages must be harmless.

### Worker adapter

Worker adapters execute provider submit/retrieve/cancel calls or internal work. They may supply evidence for `submitted`, `processing`, success, failure, or cancellation, but the Job Engine validates the active attempt, provider id, lease, retry budget, and terminal-state guard.

### Provider webhook and poller

Provider webhooks and pollers report provider status. They never update domain rows directly. Webhook correlation must use provider id, provider job id, provider account/connection scope, and an active attempt. Missing or ambiguous correlation is recorded for investigation and must not mutate a Job.

### Retry scheduler

Retry policy owns the decision to move into and out of `retry_scheduled`. It must use bounded retry counts, bounded backoff, normalized error classification, idempotency protection, and cancellation checks.

### Reconciler

The reconciler owns recovery decisions for stale leases, lost workers, missing callbacks, provider outages, and ambiguous provider states. It may requeue, retry, timeout, fail, cancel, or record no-op reconciliation evidence, but it must not bypass terminal-state immutability.

### Asset registration

Asset registration may not claim Job success. It is a downstream step inside the Job Engine completion flow. If provider success evidence is valid but asset registration fails, the Job remains non-terminal and moves to `retry_scheduled`, `failed`, or `timed_out` according to policy.

## 7. Provider Metadata Contract

Provider metadata is evidence and diagnostics, not authority.

Required rules:

- Store `provider_id` as a normalized provider identifier from the provider registry vocabulary.
- Store `provider_connection_id` when Phase 7D is available. Until then, keep legacy owner scope separate and temporary.
- Store `provider_job_id` as nullable external metadata. Do not require it for providers that complete synchronously or return callback-only references.
- Store attempt-scoped provider job ids so retries do not overwrite historical evidence.
- Store sanitized provider request/response fragments only after applying provider payload redaction and size bounds.
- Never store provider secrets, raw Authorization headers, raw API keys, bearer tokens, refresh tokens, cookies, or webhook signing secrets in provider metadata.
- Never treat provider account metadata, provider user ids, or model account names as Dynaxis users.
- Record provider capability/model identifiers as routing metadata. Governed capability/model registry ownership remains Phase 7G.
- Record webhook delivery ids or provider event ids for idempotency where providers supply them.
- Preserve provider-specific payloads only under a clearly provider-scoped field such as `provider_metadata.raw`, never as canonical Dynaxis fields.

Suggested minimum job-level metadata for WP-7E-04:

```text
job.id
job.project_id
job.generation_id nullable for non-generation jobs
job.state
job.provider_id nullable for internal jobs
job.provider_connection_id nullable until Phase 7D
job.current_provider_job_id nullable
job.capability
job.model
job.idempotency_key_hash nullable
job.attempt_count
job.max_attempts
job.cancel_requested_at nullable
job.deadline_at nullable
job.terminal_at nullable
job.error_code nullable
job.error_message nullable
job.error_retryable nullable
job.created_by_principal_type
job.created_by_principal_id nullable
job.created_at
job.updated_at
```

Suggested attempt-level metadata:

```text
attempt.id
attempt.job_id
attempt.attempt_number
attempt.state
attempt.queue_message_id nullable
attempt.lease_id nullable
attempt.worker_id nullable
attempt.provider_id nullable
attempt.provider_connection_id nullable
attempt.provider_job_id nullable
attempt.submitted_at nullable
attempt.started_at nullable
attempt.ended_at nullable
attempt.error_code nullable
attempt.error_retryable nullable
attempt.provider_metadata sanitized nullable
```

These field names are contract guidance for WP-7E-04. The migration may choose exact table names and indexes, but it must preserve the semantics.

## 8. Failure Semantics

Failures must be normalized before they affect state.

Failure classes:

- `INVALID_REQUEST`: caller input or persisted Job payload is invalid. Non-retryable.
- `AUTHORIZATION_DENIED`: Dynaxis permission or ownership check fails. Non-retryable.
- `PROVIDER_AUTH_FAILED`: ProviderConnection secret, provider account, or legacy key is invalid. Non-retryable until connection is repaired.
- `PROVIDER_RATE_LIMITED`: Provider rate limit or quota pressure. Retryable when policy budget remains.
- `PROVIDER_UNAVAILABLE`: Provider outage, 5xx, network failure, or webhook outage. Retryable when policy budget remains.
- `PROVIDER_REJECTED`: Provider accepted the request shape but rejected content, policy, model, or safety constraints. Usually non-retryable unless resolver policy changes the request.
- `PROVIDER_FAILED`: Provider reports terminal execution failure. Retryable only when provider error taxonomy says retry is safe.
- `WORKER_FAILED`: Worker crashed or returned an internal error. Retryable when the attempt can be safely replayed.
- `LEASE_EXPIRED`: Dispatcher or worker lease expired. Retryable unless provider submission ambiguity requires reconciliation first.
- `OUTPUT_INVALID`: Provider returned unusable, unsafe, missing, or unregistrable outputs. Retryable only when the adapter can produce a fresh attempt safely.
- `ASSET_REGISTRATION_FAILED`: Output was produced but Dynaxis failed to register required Assets or artifacts. Retryable if duplicate registration is prevented by idempotency.
- `CANCEL_FAILED`: Provider cancellation failed or was unsupported. It does not automatically mean the Job failed; cancellation policy decides final state.
- `TIMEOUT`: A Dynaxis deadline was exceeded. Maps to `timed_out` when retry budget is exhausted or policy forbids another attempt.

Error messages persisted to Job records must be user-safe, redacted, and bounded. Detailed provider payloads must remain sanitized diagnostics.

## 9. Cancellation Semantics

Cancellation is a Dynaxis policy decision, not a provider guarantee.

Rules:

- Only an authorized principal with `job.cancel` or an explicit internal service policy may request cancellation.
- Cancellation request records `cancel_requested_at`, requested-by actor metadata, and reason.
- If the Job is `queued`, cancellation may finalize immediately as `cancelled`.
- If the Job is `retry_scheduled`, cancellation suppresses future retries and finalizes as `cancelled`.
- If the Job is `dispatching`, `submitted`, or `processing`, the Job Engine moves to `cancelling` and asks the active adapter to cancel when supported.
- If provider cancellation is unsupported, the Job Engine may still finalize as `cancelled` after suppressing Dynaxis retries and recording that external execution may continue outside Dynaxis control.
- Late provider success after `cancelled` must not register Assets automatically.
- Late provider failure after `cancelled` is recorded as reconciliation evidence only.
- A cancelled Job may be retried only by creating a new Dynaxis Job through an authorized retry action. The original Job remains terminal.

## 10. Timeout Semantics

Timeouts are owned by Dynaxis, even when provider APIs have their own time limits.

Deadline types:

- Queue wait deadline: maximum time a Job may remain `queued` or `retry_scheduled` before dispatch.
- Lease deadline: maximum time a dispatcher/worker lease may remain active without heartbeat or ack.
- Submit deadline: maximum time an adapter may spend submitting to a provider.
- Provider acceptance deadline: maximum time after submit before the provider must expose a usable provider job id or accepted status when the provider contract requires one.
- Execution deadline: maximum wall-clock time for provider or worker execution.
- Cancellation deadline: maximum time a Job may remain `cancelling`.
- Asset registration deadline: maximum time completion may spend registering required outputs.

Timeout outcomes:

- If timeout happens before provider acceptance and retry budget remains, transition to `retry_scheduled`.
- If timeout happens after provider acceptance and the provider state is ambiguous, reconciliation must run before retrying unless the adapter declares replay safety.
- If retry budget is exhausted or policy forbids retry, transition to `timed_out`.
- A timeout transition must record which deadline was exceeded.

## 11. Retry Semantics

Retry creates a new attempt for the same Dynaxis Job. It does not create a new Generation or duplicate Assets.

Rules:

- Retry is allowed only from non-terminal states through `retry_scheduled`.
- Retry must be bounded by `max_attempts`, total execution deadline, and provider policy.
- Retry backoff must be bounded, include jitter where appropriate, and record `next_attempt_at`.
- Retry must preserve the same Dynaxis Job id.
- Retry may produce a new provider job id. Attempt history preserves all provider job ids.
- Retry must be idempotent across duplicate queue messages, duplicate user retry clicks, process restarts, and webhook redelivery.
- Manual retry of a terminal `failed` or `timed_out` Job must create a new Dynaxis Job linked to the original by provenance/retry metadata. It must not mutate the terminal state.
- Retry of `cancelled` is a new Job by definition.

Idempotency keys should bind:

```text
workspace/project scope
authorized actor or service
generation request fingerprint
capability/model/provider routing decision
client supplied idempotency key when present
```

Idempotency must prevent duplicate Jobs for repeated submit requests and duplicate Assets for repeated completion attempts.

## 12. Reconciliation Semantics

Reconciliation repairs divergence between durable Dynaxis state and external evidence.

Reconciler responsibilities:

- Find stale `dispatching`, `submitted`, `processing`, `retry_scheduled`, and `cancelling` Jobs.
- Resolve stale leases and worker crashes.
- Poll providers when webhooks are missing or delayed.
- Detect provider job ids that cannot be correlated safely.
- Detect provider terminal evidence that arrived after Dynaxis terminal state.
- Mark retryable stuck Jobs as `retry_scheduled`.
- Mark exhausted or non-retryable stuck Jobs as `failed` or `timed_out`.
- Finalize cancellation when provider cancellation is unsupported, complete, or past deadline.
- Record reconciliation decisions in the job audit timeline.

Reconciliation must be conservative:

- Do not register Assets for a terminal non-success Job.
- Do not resurrect terminal Jobs.
- Do not trust provider success without output normalization and asset registration.
- Do not infer Workspace/Project authority from provider metadata.
- Do not silently change provider, model, Project, Generation, or ownership fields.

## 13. Generation And Asset Coupling

For generation jobs:

- Job must belong to exactly one Project.
- Job must reference the canonical Generation it is executing unless a later non-generation job type explicitly allows null `generation_id`.
- Generation and Job provider ids must match for provider-backed generation work.
- Generation and Job Project ids must match.
- A Generation may point to a primary Job, but the Job remains the execution authority.
- Generation status may be projected from the primary Job state for UI/history compatibility.
- Asset records must reference the Dynaxis Job id that produced them.
- Asset records must never use provider job id as their production authority.

Recommended Generation projection:

| Job state | Generation status projection |
| --- | --- |
| `queued`, `dispatching`, `retry_scheduled` | `submitted` or future `queued` where supported |
| `submitted`, `processing`, `cancelling` | `processing` |
| `succeeded` | `succeeded` |
| `failed`, `timed_out` | `failed` |
| `cancelled` | `cancelled` |

Projection is compatibility behavior. The Job Engine remains the source of truth.

## 14. Security And Authorization

All external Job actions must pass Dynaxis authorization before reaching the Job Engine.

Rules:

- `job.create`, `job.read`, `job.cancel`, and `job.retry` use the Phase 7C policy vocabulary.
- Project-scoped inheritance is Job -> Project -> Workspace.
- Provider credentials and provider job ids do not grant Job access.
- Webhook authentication verifies provider origin only. It does not grant user authority.
- Internal service principals must be explicit, scoped, and audited.
- Worker adapters are not principals for user permissions.
- ProviderConnection use must later require Phase 7D connection ownership and use permissions.
- Job mutation APIs must reject mismatched Project, Generation, provider, owner, and active-attempt context.

## 15. Downstream Contracts

### WP-7E-03 Job Event Model and Audit Timeline

WP-7E-03 owns event schema details. It must at minimum be able to represent:

- job created
- dispatch started
- provider submitted
- provider updated
- retry scheduled
- cancellation requested
- cancellation finalized
- completed
- failed
- timed out
- reconciled

Events must correlate Job id, Project id, Generation id when present, Asset ids when created, ProviderConnection id when available, provider id, provider job id, worker id, queue lease id, request id, idempotency key hash, and actor/service provenance where applicable.

### WP-7E-04 Job Schema Migration and Persistence

WP-7E-04 must persist:

- canonical Job state and terminal timestamp
- transition timestamps
- attempts
- active leases
- idempotency keys
- provider callback lookup metadata
- sanitized provider metadata
- normalized failure fields
- cancellation and timeout fields
- event/audit timeline linkage

It must provide indexes for:

- Project history and polling by Job id
- active state scanning
- queue/lease acquisition
- retry scheduling
- provider callback correlation
- idempotency lookup
- terminal audit review

It must enforce or service-guard:

- terminal immutability
- valid transition graph
- provider/generation/project invariants
- no destructive rewrite of existing jobs
- no direct provider-owned lifecycle mutation

### WP-7E-05 Queue Implementation and Dispatcher

WP-7E-05 must treat queue messages as delivery hints. Durable state, lease validity, retry budget, cancellation, and terminal-state checks live in the Job Engine.

### WP-7E-06 Worker Runtime and Provider Worker Adapter

WP-7E-06 must implement worker lifecycle behavior without making workers lifecycle authorities. Workers may lease Jobs, heartbeat active attempts, submit/retrieve/cancel through provider adapters, and report artifacts or provider evidence back to the Job Engine. Heartbeat expiry, cancellation observation, artifact reporting, provider handoff, and provider response normalization must all pass through Job Engine transition validation before mutating Job, Generation, Asset, attempt, or audit state.

### WP-7E-07 Webhook Ingress and Verification

WP-7E-07 must verify provider webhook authenticity and delivery idempotency before passing evidence to the Job Engine. A valid webhook is not sufficient to mutate a Job unless correlation and transition validation pass.

### WP-7E-08 Retry Timeout Cancellation and Idempotency

WP-7E-08 must implement the policies defined in Sections 9, 10, and 11 without changing the canonical state vocabulary or terminal rules.

### WP-7E-09 Recovery Reconciliation Observability

WP-7E-09 must implement reconciliation based on Section 12 and expose operator-visible decision evidence without making manual observation a bypass of Job Engine transition rules.

## 16. Non-Goals

This specification does not implement:

- runtime queue selection
- worker loop behavior
- webhook routes
- schema migrations
- provider connection storage
- secret management
- provider adapters beyond the Phase 7B contract
- capability/model registry persistence
- billing, credit holds, or cost accounting
- product UI changes
- public API contract changes

WP-7E-01 is complete when reviewers can confirm:

- Canonical states and terminal states are named and defined.
- Allowed transitions are listed with transition ownership.
- Forbidden transitions and terminal-state immutability are explicit.
- Dynaxis Job id and provider job id are distinct.
- Provider metadata is scoped, sanitized, and non-authoritative.
- Failure, cancellation, timeout, retry, and reconciliation semantics are specified.
- The Job Engine authority boundary is explicit.
- WP-7E-03, WP-7E-04, WP-7E-05, WP-7E-06, WP-7E-07, WP-7E-08, and WP-7E-09 have enough contract detail to proceed without inventing the state architecture.
