# Objective

Deliver Project Membership Schema and Role Model for Phase 7C. The result must be directly usable by the next assigned coding agent without requiring that agent to invent architecture, schema semantics, service boundaries, or security rules.

# Context

Dynaxis owns Projects, Jobs, Assets, identity, graph, memory, orchestration, and verification. This Work Package is intentionally narrow: it must deliver Project Membership Schema and Role Model without reinterpreting the roadmap or absorbing adjacent package scope.

# Required Deliverables

- `dynaxis_project_members` table referencing `dynaxis_projects.id`, Better Auth `auth.organization.id`, and `auth.user.id`
- Project role enum/check vocabulary: `owner`, `admin`, `editor`, `viewer`
- unique `(project_id, user_id)` membership invariant and indexes for project/user lookup
- delete behavior: cascade when the canonical Project is deleted, restrict or cascade only where Better Auth user/org semantics justify it; organization deletion must not silently orphan project access
- No authorization evaluator in this package; expose only schema constants and role parsing helpers if needed by later services
- Organization-owned project invariant: member `organization_id` must equal the project owning workspace and the user must be a Better Auth member of that workspace
- Personal workspace compatibility: personal projects may only grant membership to the personal workspace owner until later org-sharing rules explicitly allow more

# Contracts That Must Not Change

- Dynaxis Project remains the canonical Project; do not create another Project entity.
- Better Auth remains the workspace authentication and organization-membership primitive.
- Provider credentials, model accounts, and worker adapters must not become user identity.
- Dynaxis Jobs, permissions, Project ownership, provenance, and verification gates must not be bypassed.
- Marketplace, App Factory, Skills, and Plugin work must use canonical registries instead of duplicating them.

# Acceptance Criteria

- A project membership row cannot reference a non-existent Project, Workspace, or user.
- Duplicate memberships for the same project/user are rejected by the database.
- The package does not add or modify route authorization logic.

# Validation

- schema-shape tests for FKs, uniqueness, roles, and migration SQL
- negative tests proving non-workspace users cannot be represented as project members
- Run `npm run program:status` when Work Package metadata changes.
- Run `git diff --check` before handoff.
