# Objective

Deliver the minimum canonical persistence correction required to unblock
WP-7C-14 (Route Migration: Projects and Assets): canonical Workspace/Project-
scoped create/read/list/update access to Dynaxis Projects and Assets that does
not depend on the legacy `owner_ref` partition. This Work Package changes
persistence for Projects and Assets only; no other domain is touched.

# Context

WP-7C-14 requires migrating Projects and Assets onto the canonical AuthContext
route boundary, authorizing through `AuthContext -> Workspace -> Project ->
Project membership/role -> resource inheritance`. That migration is blocked
because the Project and Asset persistence layer is entirely `owner_ref`-
partitioned: `dynaxis_projects.owner_ref` and `dynaxis_assets.owner_ref` were
`NOT NULL`, the only `owner_ref` scheme is the legacy `ak_sha256:<api-key-hash>`,
and the store exposed only `owner_ref`-keyed read/write methods. A canonical
Better Auth principal has no legacy `owner_ref`, so it could neither create nor
discover canonical Projects/Assets.

This Work Package owns the persistence changes needed to close that gap for
Projects and Assets. It does not migrate any route, service, or authorization
code; WP-7C-14 consumes this bridge. Equivalent gaps in other domains
(Generations, Jobs, Characters, Products, Brands, Campaigns, Compositions,
Design) are explicitly out of scope and are owned by whichever future Work
Package the programme assigns.

# Required Deliverables

- `dynaxis_projects.owner_ref` and `dynaxis_assets.owner_ref` nullable so
  canonical rows persist `organization_id` (Projects) / `project_id` inheritance
  (Assets) with `owner_ref IS NULL`; legacy rows keep populating `owner_ref`.
- Canonical store operations on both the PostgreSQL store and the memory store:
  - `createCanonicalProject({ organizationId, userId, ... })` — atomic Project +
    explicit creator Project membership (role `owner`) in one transaction; a
    failed membership insert rolls the Project back, so creation never leaves an
    orphan Project. The membership row lives in the existing
    `dynaxis_project_members` table so the database's Project membership
    invariants (including the Better Auth workspace-member FK) apply unchanged.
    Only the creator receives this membership; Workspace owner/admin never
    implies Project owner.
  - `getCanonicalProject(projectId)`
  - `updateCanonicalProject({ projectId, organizationId }, patch)`
  - `listCanonicalProjectsForUser({ organizationId, userId, includeArchived })`
    — only Projects the user is an explicit `dynaxis_project_members` member of;
    Workspace membership alone reveals nothing.
  - `getCanonicalDefaultProjectForUser({ organizationId, userId })` — Default
    Project resolution also requires the user's explicit membership, so a shared
    Workspace never exposes another member's Default Project.
  - `createCanonicalAsset({ projectId, ... })`, `getCanonicalAsset(assetId)`,
    `listCanonicalAssetsForProject({ projectId, generationId, limit })`
  - `findAssetOwnership(assetId) -> { type: 'asset', id, projectId, organizationId } | null`
    — trusted ownership metadata with `organizationId` resolved
    Asset -> Project -> `dynaxis_projects.organization_id`, never caller input;
    `null` for a missing Asset; `organizationId: null` under an unprojected
    legacy Project.
- Memory-store parity for exactly these operations; no future-domain APIs.

# Contracts That Must Not Change

- Dynaxis Project remains the canonical Project; no second Project entity or
  membership model.
- Legacy `owner_ref` methods are unchanged; canonical and legacy partitions stay
  isolated; no canonical method falls back to `owner_ref`; no `owner_ref`
  parameter is overloaded with a Workspace or user id.
- No `organization_id` column is added to `dynaxis_assets` or any other table.
- No authorization, identity, Better Auth, or Project membership kernel change.

# Acceptance Criteria

A Better Auth user with no historical `x-api-key` can:

1. create a canonical Project;
2. receive explicit Project owner membership transactionally;
3. list only Projects they explicitly belong to;
4. resolve their Default Project safely;
5. create/read/list canonical Assets through Project ownership.

Nothing beyond those five.
